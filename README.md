# NABDH · AI Maintenance Platform

**Enterprise-grade Predictive & Prescriptive Maintenance System — v4.1.0**

An end-to-end industrial AI platform that ingests real-time sensor readings, predicts equipment failures before they happen, explains every decision with SHAP, and prescribes prioritized maintenance actions. Built for NABDH industrial environments.

---

## Overview

| Layer | Technology | Role |
|---|---|---|
| Machine Learning | Random Forest + SHAP | Failure prediction & explainability |
| Backend API | FastAPI + Uvicorn | REST endpoints, alerts, audit log |
| Authentication | JWT + RBAC + Redis | Secure token-based access control |
| Dashboard | Streamlit | Live monitoring & analytics UI |
| Database | SQLite (WAL mode) | Zero-dependency persistence |
| Token Store | Redis (in-memory fallback) | Token revocation & session management |
| Containerization | Docker + Compose | Production-ready deployment |

## Features

### Prediction Engine
- **Binary failure classification** with calibrated confidence scores
- **5 failure modes** — Thermal Overload, Mechanical Failure, Electrical Fault, Pressure Anomaly, Environmental Stress
- **Health Score** (0–100) representing overall asset condition
- **Time-to-Failure estimation** in hours
- **SHAP explainability** — top contributing features per prediction
- **Sensor anomaly detection** — flags out-of-range readings automatically
- **Confidence trend analysis** — detects rising or falling risk trajectories

### Authentication & Security (v4.1.0)
- **JWT access tokens** (1h TTL) + **refresh tokens** (7d TTL) with automatic rotation
- **RBAC** — three roles: `viewer` (read-only) → `operator` (predict + acknowledge) → `admin` (full access)
- **Redis-backed token revocation** — revoked tokens are rejected immediately
- **Refresh token reuse detection** — reuse wipes all user sessions and logs a CRITICAL event
- **Password policy enforcement** — min 8 chars, uppercase, digit, special character
- **Security audit log** — every auth event stored in DB with trace ID, IP, user-agent
- **Rate limiting** — 100/min global, 30/min on `/predict`, 10/min on `/predict_batch`
- **Pydantic v2 strict validation** — physical range checks on all sensor inputs

### Prescriptive Maintenance
- Rule-based prescriptive engine maps failure modes → prioritized action lists
- Actions ranked by `CRITICAL / HIGH / MEDIUM / LOW` priority
- Persisted per-prediction for audit and review

### Root Cause Analysis (RCA)
- Causal chain reconstruction from SHAP values + sensor metadata
- Primary cause identification + inspection recommendation
- Queryable via `/rca/{request_id}` endpoint

### Drift Detection
- Kolmogorov-Smirnov test on rolling prediction window vs. reference data
- Configurable window size, threshold, and feature limit
- Automatic retrain flag when drift is detected
- Full drift history queryable via API

### Alerting
- Alerts fired when `confidence ≥ ALERT_MIN_CONFIDENCE` (default 0.85) and prediction = failure
- Acknowledge workflow via `POST /alerts/{id}/acknowledge`
- Optional webhook delivery (Slack / Teams / custom URL)

### Observability
- Full API audit log — every request, latency, status code, IP
- Security audit log — every auth event with severity and trace ID
- Rolling performance metrics — failure rate, avg/P95 latency
- SQLite WAL mode — concurrent read/write without locking

## Quick Start

### Prerequisites

- Python 3.10 or higher
- pip

### 1 — Install dependencies

```bash
pip install -r requirements.txt
```

### 2 — Configure environment

```bash
cp .env.example .env   # Linux/macOS
copy .env.example .env  # Windows
```

Edit `.env` and set real values for `JWT_SECRET_KEY` and all passwords. Leave `REDIS_URL` empty for local development (uses in-memory fallback).

### 3 — Train the model

Run once to generate all ML artifacts:

```bash
python train.py
```

This produces `pipeline.pkl`, `expected_columns.pkl`, `model_version.json`, and `reference_data.csv`.

### 4 — Start the platform

**Windows (recommended):**
```bat
run_project.bat
```

**Linux / macOS:**
```bash
chmod +x start.sh
./start.sh
```

Both scripts auto-create `.env`, auto-train if artifacts are missing, then launch the API and dashboard.

| Service | URL |
|---|---|
| Dashboard | http://localhost:8501 |
| API | http://localhost:8000 |
| Interactive API Docs | http://localhost:8000/docs |
| ReDoc | http://localhost:8000/redoc |

**Default credentials (from .env):**

| Username | Role | Permissions |
|---|---|---|
| `admin` | Admin | Full access — audit, register users, all endpoints |
| `operator` | Operator | Predict, acknowledge alerts |
| `viewer` | Viewer | Read-only — history, analytics, alerts |

## Docker Deployment

### Build and run all services (Redis + API + Dashboard)

```bash
# Build artifacts first (required once)
python train.py

# Start all services
docker-compose up --build
```

Redis is started automatically and the API waits for it to be healthy before starting.

### Stop

```bash
docker-compose down
```

Prediction data, alert history, audit logs, and Redis data persist across restarts via Docker volumes (`nabdh-data`, `nabdh-redis-data`).

## API Reference

All endpoints (except `/health` and `/auth/login`) require a **Bearer JWT token** in the `Authorization` header.

### Authentication Flow

```bash
# 1 — Obtain tokens
curl -X POST http://localhost:8000/auth/login \
  -d "username=admin&password=Admin@2024!"

# 2 — Use access token
curl http://localhost:8000/status \
  -H "Authorization: Bearer <access_token>"

# 3 — Refresh before expiry (automatic in dashboard)
curl -X POST http://localhost:8000/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{"refresh_token": "<refresh_token>"}'
```

### Auth Endpoints

| Method | Endpoint | Role | Description |
|---|---|---|---|
| `POST` | `/auth/login` | Public | Obtain access + refresh tokens |
| `POST` | `/auth/refresh` | Public | Rotate refresh token, get new pair |
| `POST` | `/auth/logout` | Any | Revoke current session |
| `POST` | `/auth/register` | Admin | Create a new user account |
| `GET` | `/auth/me` | Any | Return current user info |

### System

| Method | Endpoint | Role | Description |
|---|---|---|---|
| `GET` | `/health` | Public | Health check — no auth required |
| `GET` | `/status` | Admin | Full system health, model info, drift status, uptime |
| `GET` | `/metrics` | Admin | Rolling-window performance metrics |
| `GET` | `/audit` | Admin | Full API request audit log |
| `GET` | `/audit/security` | Admin | Security event log — login attempts, token reuse, 401s |

### Prediction

| Method | Endpoint | Role | Description |
|---|---|---|---|
| `POST` | `/predict` | Operator+ | Single-record prediction with full enrichment |
| `POST` | `/predict_batch` | Operator+ | Batch prediction — up to 100 records |

**Example — single prediction:**

```bash
curl -X POST http://localhost:8000/predict \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{
    "sensor_1": 88.0,
    "sensor_2": 270.0,
    "sensor_3": 60.0,
    "sensor_4": 430.0,
    "sensor_5": 50.0,
    "sensor_6": 45.0,
    "sensor_7": 44.0,
    "sensor_8": 100.0,
    "sensor_9": 82.0,
    "sensor_10": 72.0
  }'
```

Send `null` for any sensor to simulate a missing reading — the imputer handles it automatically.

**Prediction response fields:**

| Field | Type | Description |
|---|---|---|
| `prediction` | `0` or `1` | 0 = Normal, 1 = Failure |
| `confidence` | `float` | Model confidence (0.0 – 1.0) |
| `severity` | `string` | `HIGH / MEDIUM / LOW / NONE` |
| `recommendation` | `string` | Human-readable action recommendation |
| `health_score` | `float` | Asset health index (0 – 100) |
| `time_to_failure_hours` | `float` | Estimated hours until failure |
| `failure_mode` | `string` | Identified failure category |
| `top_factors` | `list` | Top SHAP-ranked contributing sensors |
| `shap_values` | `dict` | Full per-feature SHAP values |
| `prescriptive_actions` | `list` | Ordered maintenance actions |
| `maintenance_priority` | `string` | Highest action priority `P1 / P2 / P3` |
| `rca` | `dict` | Causal chain and primary cause |
| `alert` | `bool` | True if alert threshold exceeded |
| `alert_message` | `string` | Alert description when alert is true |
| `sensor_anomalies` | `list` | Sensors with out-of-range values |
| `anomaly_warning` | `string` | Human-readable anomaly summary |
| `confidence_trend` | `string` | `RISING / FALLING / STABLE` |
| `trend_alert` | `bool` | True if confidence spike detected |
| `model_version` | `string` | Version of the active model |
| `latency_ms` | `float` | End-to-end inference time |

## Configuration

All settings are environment-variable driven. Copy `.env.example` to `.env` and fill in your values.

| Variable | Default | Description |
|---|---|---|
| `JWT_SECRET_KEY` | *(required)* | Secret key for signing JWT tokens — min 32 chars |
| `JWT_ALGORITHM` | `HS256` | JWT signing algorithm |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `60` | Access token lifetime in minutes |
| `REFRESH_TOKEN_EXPIRE_DAYS` | `7` | Refresh token lifetime in days |
| `REDIS_URL` | *(empty)* | Redis connection URL — leave empty for in-memory fallback |
| `ADMIN_USERNAME` | `admin` | Admin account username |
| `ADMIN_PASSWORD` | *(required)* | Admin account password — must meet password policy |
| `OPERATOR_USERNAME` | `operator` | Operator account username |
| `OPERATOR_PASSWORD` | *(required)* | Operator account password |
| `VIEWER_USERNAME` | `viewer` | Viewer account username |
| `VIEWER_PASSWORD` | *(required)* | Viewer account password |
| `RATE_LIMIT` | `100/minute` | Global API rate limit |
| `THRESHOLD` | `0.70` | Failure confidence cutoff |
| `ALERT_MIN_CONFIDENCE` | `0.85` | Minimum confidence to fire an alert |
| `DATABASE_PATH` | `nabdh.db` | SQLite file path |
| `DRIFT_WINDOW_SIZE` | `500` | Rolling window for drift detection |
| `DRIFT_KS_THRESHOLD` | `0.05` | KS-test p-value threshold |
| `MIN_SAMPLES_DRIFT` | `50` | Minimum samples before drift check runs |
| `ALERT_WEBHOOK_URL` | *(empty)* | Slack / Teams webhook URL for push alerts |
| `ALLOWED_ORIGINS` | `http://localhost:8501` | Comma-separated CORS origins |
| `BACKEND_URL` | `http://127.0.0.1:8000` | Dashboard → API base URL |

**Password policy:** minimum 8 characters, at least one uppercase letter, one digit, and one special character (`!@#$%^&*`).

## Failure Modes

| Mode | Trigger Sensors | Description |
|---|---|---|
| `THERMAL_OVERLOAD` | sensor_1, sensor_7 | Temperature or ambient heat beyond safe limits |
| `MECHANICAL_FAILURE` | sensor_4, sensor_10 | Abnormal RPM or excessive vibration |
| `ELECTRICAL_FAULT` | sensor_5, sensor_6, sensor_8 | Voltage, current, or frequency deviation |
| `PRESSURE_ANOMALY` | sensor_2, sensor_9 | Over-pressure in primary or secondary circuit |
| `ENVIRONMENTAL_STRESS` | sensor_3 | Humidity-driven corrosion or condensation risk |

## Dashboard

The Streamlit dashboard provides a full monitoring interface with JWT-authenticated access.

| Tab | Content |
|---|---|
| **Prediction** | Live sensor rings, run analysis, SHAP waterfall, health gauge, prescriptive actions, RCA |
| **System** | API status, model version, prediction counts, latency metrics, drift flag |
| **Drift Report** | Feature-level KS-test results, drifted feature list, retrain recommendation |
| **History** | Confidence timeline, severity donut, full record table with 200-row default |
| **Analytics** | Configurable time window, failure rate, health trend chart, failure mode distribution |
| **Alerts** | Alert center with severity badges, acknowledge workflow, unacknowledged filter |

**Left panel** — sensor sliders stay sticky while tab content scrolls independently. Token refresh happens silently in the background — sessions stay alive without re-login.
